## 远场选型与官方对齐（2026-09-23）

### 远场实测与选型

笔记本放茶几，身后约 2 米电视播放同一档综艺（非连续对话、多人、广告），房间里另有一人随机说话，三个 GGUF 各录 5 分钟，浏览器降噪开启（产品默认配置）。两轮顺序均为 F16 → Q8 → Q4；第二轮唯一变动是电视音量调高两格。无字幕、无参考文本，因此按三方共识与语义判读评估：相互印证的内容视为听到的核心，只有一方的内容视为该方误差。原始导出含房间人声，留在本机 `results/`，不纳入 Git。

| | 轮1 语义得分 | 轮2 语义得分 | 轮1 孤立率 | 轮2 孤立率 | 超 160 ms 步 | 跨轮自一致 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| F16 | 75%（16.5/22） | 70.8%（17/24） | 32.3% | 21.6% | 8.9% / 9.7% | 556 字 |
| Q8_0 | 80%（17.5/22） | 71.2%（18.5/26） | 41.1% | 21.8% | **5.9% / 5.9%** | 438 字 |
| Q4_K_M | 41%（9/22） | 48.1%（12.5/26） | 50.5% | 28.1% | 7.4% / 9.8% | 313 字 |

语义得分以片中念稿段（人物卡、剧情旁白）和可判定的对话点逐项判断，同义改写不算错。孤立率为 ≥6 字连续片段与另两者都不匹配的比例。轮 1 Q8 的孤立率有约 2.8 点来自开头 14 个繁体字（内容正确、字形不同），归一化后为 38.3%。

结论：**Q8 与 F16 两轮互有胜负、无法区分，选定 Q8**；Q4 两轮都明显垫底，且有语义反转（「不要用台词去交代」→「都要用」）与凭空插入，不采用。同一短语「拿回属于自己的一切」轮 1 F16 对 Q8 错、轮 2 反过来，说明单点错误不可用于给模型定性。音量调高后三者差距同时收窄，量化损伤在低信噪比下被放大；第二轮是较乐观的条件。Q8 两轮各出现一次跳出简体字符集（繁体 / 拉丁拟声词），另两者没有。

六次单步中位耗时 134–137 ms、积压最大均 160 ms、零合并，三者实时性相同；Q4 虽权重最小，均值与 p99 反而最差。

### 内存

连续 270 秒推理后的稳态 RSS：F16 12.86 GiB、Q8 11.68 GiB、Q4 10.92 GiB，每步约 15 MB 线性增长后饱和。原因是 llama-server 默认 `--cache-ram 8192` 的 prompt 状态缓存：每步音频都不同，缓存永远无法命中。同样 400 步对照，`--cache-ram 0` 的增量从 5118 MB 降到 21 MB，逐步输出 400/400 一致，耗时不变；应用改用后，Q8 连续 270 秒 RSS 为 2699 MB。连续约 13 分钟后单步中位从 134.8 ms 升到 142.7 ms，为热降频；一小时连续运行未实测。

### 与官方源码对齐

`.research/` 中的 `r2t2/r2t2_asr.py`、`ws_server.py` 与官方仓库 `80c22e6` 逐字节一致，在最新 `c461192` 也未改动。核对后补齐：标点上下文归一；尾部重复循环检测与解码器重建（检测范围为上次重建以来的文字，与官方 `last_fixed_asr_text` 一致）；无 VAD 时 60 秒安全重建；日文、韩文、西班牙文；热词上限 4000 字；提示词 system 段去掉多余换行，与模型自带 `chat_template.json` 及官方 `build_asr_prompt` 逐字节一致。

## 单步成本模型

拆解每一步的耗时来源（GGUF 用 llama.cpp `/completion` 返回的 `timings`，MLX 逐阶段 `mx.eval` 后计时）：

| | GGUF | MLX |
| --- | --- | --- |
| 固定开销 | 约 31 ms（mmproj 音频编码，按 30 s 分块补齐） | mel 预处理 5–11 ms + 音频编码 35–54 ms |
| 随窗口增长 | 0.77 ms × 音频 token（约 13 token / 秒音频） | 0.66 ms × 序列长 |
| 随生成增长 | 约 9 ms / token | 约 26 ms / token |
| 传输 | HTTP / JSON / base64，8 s 窗口约 14.5 ms | 无（同进程） |

两侧的可变成本都由窗口长度驱动，这是唯一的大杠杆。缓存命中可证明 `prompt_ms` 包含音频编码：同一段音频重复请求时 `prompt_n` 从 178 降到 1、`prompt_ms` 从 258 ms 降到 19 ms。

MLX 的 26 ms / token 相当于只跑到约 154 GB/s，而 M1 Max 有 400 GB/s 带宽；这是 mlx-audio 在 BF16 权重上的实现表现，未做量化尝试。

## 优化前的问题

原策略为上游的 16 秒窗口 / 8 秒裁剪、每 160 ms 一步、不合并。45 秒连续中文语音实测：

| 后端 | 实时系数 | 单步中位 | 结果 |
| --- | ---: | ---: | --- |
| GGUF F16 | 1.17x | 194 ms | 约 61 秒后触发 10.24 秒积压上限中止 |
| MLX BF16 | 1.64x | 248 ms | 更早中止 |

步预算是 160 ms，两者都超。对着电视连续人声测试时约一分钟必然停止，与推算一致。

## 当前策略与端到端结果

**已采纳方案 A**：保留 8 秒窗口 / 4 秒裁剪，以 160 ms 为常规推进粒度；仅在积压时合并。160 ms 是音频步长，不保证每步都有新字，也不是端到端文字延迟。

窗口改为 8 秒 / 4 秒；落后时一步最多合并 3 个分块，并按合并块数放大该步 token 预算。通过真实 FastAPI 服务与 WebSocket，按真实音频时钟发送 87.62 秒连续中文语音：

| 后端 | 音频 | 墙钟 | 单步中位 | 最大积压 | 步数 | 合并步 | 文字 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| GGUF F16 | 87.62 s | 87.79 s | 136.1 ms | 160 ms | 547 | 0 | 260 / 260 字，13 / 13 遍 |
| MLX BF16 | 87.62 s | 87.93 s | 159.4 ms | 320 ms | 537 | 10（1.9%） | 258 / 260 字，12 / 13 遍 |

两者确认文字全程只追加，没有回删。GGUF 全程无需合并；MLX 在 537 步中有 10 步合并了 2 个分块，最大积压 320 ms。事件明细见本机 `artifacts/gguf-88s.json`、`artifacts/mlx-88s.json`。

统计口径：步数包含最终刷新，耗时中位数也包含该步；合并比例为 10 / 537 ≈ 1.9%。文字计数剔除标点后，以「之前有顾客自己带酒水也没加收钱或者不让喝」（20 字）重复 13 遍为参照。原始事件重新核算得到 GGUF 260 字、13 次完整句匹配，MLX 258 字、12 次完整句匹配；MLX 第 8 遍缺少「之前」。2 / 260 ≈ 0.77% 仅是这段重复样本的漏字比例，不是一般场景的准确率下降。GGUF 的“无需合并”也不等于始终零积压，记录中的最大积压为 160 ms。

```bash
.venv/bin/python scripts/smoke.py --backend gguf --repeat 13 --output artifacts/gguf-88s-recheck.json
```

## 窗口长度的精度代价

前次开发记录称：同一段 87.62 秒音频、MLX 后端、离线逐分块喂入（不触发合并、无时间压力），只改窗口，得到下表。本次接续未找到该离线 A/B 的原始输出或专用脚本，因此这些是前次报告值，尚未独立复核；上面的实时事件文件不能代替离线对照证据。

| 窗口 | 识别字数 | 完整重复 |
| --- | ---: | ---: |
| 8 s / 4 s | 258 / 260 | 12 / 13 |
| 16 s / 8 s | 260 / 260 | 13 / 13 |

原文“第 8、13 遍开头各丢一次「之前」”与少 2 字的统计不符，已撤去；现存实时记录只支持第 8 遍漏 2 字。重复样本不能确定真实综艺、连续对话的精度差异，也不能单凭实时结果把漏字归因于窗口长度。用户已选择保留 8 秒窗口：优先维持常规 160 ms 推进粒度，接受仍需真实场景验证的精度取舍。按此前 16 秒窗口约 248 ms / 步的测量，160 ms 单步无法持续跟上输入，需要频繁合并；320 ms 是两块合并时的音频推进粒度，不是已实测保证的固定文字更新间隔。

## 已排除的优化方向

以下都做过实测，收益为零或为负，记录在此避免重复尝试：

- **llama.cpp `-fa`**：默认 `auto` 已启用 flash attention，显式 `-fa on` 与默认无差异（186.3 vs 186.1 ms）；`-fa off` 反而慢约 3%。
- **llama.cpp `-ub` / `-b`**：实际 prefill 只有 178–230 token，小于默认 ubatch 512，整个 prefill 本来就是单批，调节无意义。
- **客户端 WAV 编码与 base64**：合计 0.7 ms，可忽略。
- **MLX 微优化**：把 `_eos_token_ids()` 提出 token 循环、绕过 `generate_step` 里对 151k 词表的 `logsumexp`、把 `_build_inputs_embeds` 的逐 token Python 循环向量化，三者合计 ±3 ms，在噪声内；输出完全一致。已放弃。
- **token 预算 4 → 2**：省约 10 ms，但会吞掉句首的字。否决。
- **模型量化**：此节写作时未尝试。其后接入了官方 Q8_0 与 Q4_K_M 并做了远场选型，见上文「远场选型与官方对齐」。

## 测量陷阱

做这些测量时踩到并确认的坑，后续复测必须避开：

1. **llama.cpp 的 prompt cache**。重复送同一段音频会命中缓存，跳过音频编码：12 秒窗口下 67 ms（命中）vs 218 ms（真实流式）。任何复用音频的基准都无效，必须每次滑动音频。
2. **跨配置的缓存残留**。同一个 llama-server 上连续测多组配置时，后一组若走过前一组相同的窗口边界会命中缓存。每组配置必须重启服务并轮换音频内容。
3. **热降频**。连续 GPU 负载 20 分钟后整机变慢。生成阶段耗时是好探针：它与 `-ub`、线程数无关，若它从 37 ms 跳到 67 ms，说明是降频而非配置生效。

## 静音

4 秒数字零值静音输入，两种模型都返回空文字，包含最终刷新。数字静音不等于真实风扇、键盘声或人群背景声；这些留给实际麦克风人工判断。
