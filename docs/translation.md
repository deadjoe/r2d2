# 实时翻译为中文

2026-09-23；Apple M1 Max，64 GB；llama.cpp 0.4.1 / b29c606e2；识别固定用 GGUF Q8_0。

## 选型

| 候选 | 体积 | 结论 |
| --- | ---: | --- |
| **腾讯 HY-MT1.5-1.8B，Q4_K_M** | 1.13 GB | 采用。专用翻译模型，33 种语言互译，覆盖本应用的英、日、韩、西；官方发布 GGUF，与识别同走 llama.cpp |
| TranslateGemma 4B | 约 2.5 GB 起 | 参数量是前者两倍多 |

| NLLB-600M、opus-mt | 很小 | 质量低一档；NLLB 为非商用许可 |

权重来自 `tencent/HY-MT1.5-1.8B-GGUF` 固定版本 `265b2e615a7dc9b06c435dc878829ad99a512ba2`，SHA-256 与官方 LFS 元数据一致，记入 `models-manifest.json`。许可为腾讯混元社区许可（不适用于欧盟、英国、韩国），见 `third_party/NOTICE.md`。

## 为什么放在 CPU 上

识别 Q8 每 160 ms 一步、单步约 130 ms，Metal 队列本来就占了约八成。按真实音频时钟重放 33.8 秒官方示例（重复 5 遍），同时让翻译模型不停歇地连续翻译两句英文（最坏情况）：

| 条件 | 识别单步中位 | p90 | 超 160 ms 的步 | 合并步 | 最大积压 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 只跑识别 | 131 ms | 146 ms | 5% | 0 | 160 ms |
| 翻译在 GPU，连续不停 | 166 ms | 196 ms | **63%** | 16 | 320 ms |
| 翻译在 GPU，每次间隔 300 ms | 146 ms | 181 ms | 31% | 0 | 160 ms |
| **翻译在 CPU（6 线程），连续不停** | **127 ms** | 150 ms | **4%** | 0 | 160 ms |

翻译进 GPU 会直接把识别推过 160 ms 预算；放在 CPU 上与只跑识别无法区分。单句翻译耗时（同一批英、日、韩、西测试句，贪心解码）：

| 位置 | 解码速度 | 单句耗时 |
| --- | ---: | ---: |
| Metal | 约 140 token/s | 70–185 ms |
| CPU 8 线程 | 约 65 token/s | 190–610 ms |
| **CPU 6 线程** | 约 65 token/s | 210–535 ms |
| CPU 4 线程 | 约 55 token/s | 285–675 ms |

取 6 线程：比 4 线程快约三成，8 线程几乎不再变快，还给其他应用留出核心。可用 `R2D2_MT_THREADS` 覆盖。翻译进程内存约 1.2 GB，与识别的 2.7 GB 合计约 4 GB。事件原件在本机 `artifacts/mt/interference/`。

## 显示策略

与识别的白字 / 灰字同构：

1. **定稿（白字）**：识别已确认的文字一出现句末标点（`。！？!?`；英文句点须后接空白才算，避免 `3.5`），这一句就翻译一次，追加到译文末尾，此后不再改动。未见标点时，按加权长度（中日韩字符记 2）超过 120 切一次，优先切在逗号等分句标点，其次空格。停止时剩余文字整体定稿。
2. **草稿（灰字）**：未完句（已确认尾巴 + 识别灰字）每次变化都重译，新的替换旧的；翻译忙时只保留最新版本，中间版本直接跳过。定稿句总是先于草稿处理，所以翻译慢只会让草稿不够新，不会打乱定稿顺序。
3. 若一句定稿时的原文与最后一次草稿完全相同，直接复用草稿译文，不再调用模型（贪心解码下结果相同）。日文样本中大多数句子如此，定稿延迟中位数为 0。
4. 一句定稿时，若当前草稿覆盖了这一句（按原文位置判断，不比较文字，因为识别会把 `ten` 改成 `10`），立即清掉草稿，避免同一句在白字和灰字中各出现一次。
5. 中文不翻译：识别语言选中文时根本不加载翻译模型；自动识别下逐句判断，汉字占多数且无假名、谚文的句子原样通过。
6. 翻译失败或模型缺失时只发一次 `translation_error`，识别照常进行。

前缀缓存：请求带 `cache_prompt: true`，复用翻译进程槽位里与上一次调用相同的前缀（固定模板，以及逐字增长的草稿原文的大部分）。在测试集的真实句子上按草稿逐步增长的方式重放（CPU 6 线程，只跑翻译）：英文每次调用 218 → 127 ms，韩文 499 → 346 ms，日文 341 → 219 ms，节省全部来自 prompt 处理，生成耗时不变。复用会改变计算的分批，同一原文的措辞可能随前一次调用略有不同（韩、日各约一半句子有措辞差异，逐句对照未见质量高低）；定稿与最后一次草稿原文相同时仍直接复用草稿译文，所以定稿不会因此跳变。`--cache-ram 0` 不变，槽位内 KV 不额外占内存。实时会话中翻译进程约 75% 的时间在工作，其中约 88% 是草稿重译，见本机 `artifacts/bench/`。

没有采用的做法：

- **模型卡的上下文翻译模板**：把前一两句作为上文时，1.8B 会把上文也译进输出（例如「東京の天気はどうですか。」成了译文的一部分，「Um, uh, so」被译成上文内容）。改用逐句的基础模板，也更快。
- **模型卡推荐的采样参数**（temperature 0.7）：同一草稿反复重译会无故跳动，改为贪心。
- 模型给未完句加的「……」在定稿和草稿中都去掉（原文本身以省略号结尾时保留），光标已表达「未完」。

## 端到端实测

`say` 合成的英、日、韩、西语音（干净的 TTS，只验证流程与延迟，不代表真实场景准确率），经真实 FastAPI 服务与 WebSocket 按音频时钟发送，识别 Q8 + 翻译 CPU：

| 语言 | 音频 | 识别单步中位 | 超 160 ms | 最大积压 | 合并 | 定稿句 | 定稿延迟中位 / 最大 | 草稿更新 | 停止后收尾 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 英文 | 53.6 s | 123 ms | 6% | 160 ms | 0 | 13 | 660 / 995 ms | 121 | 642 ms |
| 日文 | 40.1 s | 128 ms | 6% | 160 ms | 0 | 9 | 0 / 305 ms | 91 | 306 ms |
| 韩文 | 23.6 s | 127 ms | 4% | 160 ms | 0 | 6 | 426 / 999 ms | 51 | 282 ms |
| 西班牙文 | 34.7 s | 124 ms | 4% | 160 ms | 0 | 6 | 750 / 1628 ms | 65 | 361 ms |

「定稿延迟」是识别确认一句到该句译文定稿的时间。四种语言下识别均未受影响，定稿译文全程只追加。西班牙文样本识别本身较差（`Buenas` → `Wena's`），且以逗号代替句号，靠长度切句，所以延迟最高；翻译会忠实地译出识别错误。事件原件在 `artifacts/mt/`。

Chrome 中验证了英文导入音频的完整流程、灰字草稿、定稿、「复制译文」、听感记录里的译文和 390 px 窄屏布局；控制台只有既有的 favicon 404。未打开物理麦克风。

复测：

```bash
./server.sh start
.venv/bin/python scripts/smoke.py --backend gguf_q8 --audio artifacts/mt/en.wav --language English --translate --output artifacts/mt/en-q8.json
```

## 局限

- 1.8B 偶尔会增添原文没有的内容（例如把「small models are accurate」译成「就已经足以满足需求了」）。需要更高质量时可换 Q6_K（1.47 GB），`r2d2/translate.py` 的 `MT_FILE` 一行即可，速度会慢一些。
- 句子边界完全依赖识别给出的标点。长时间不打句号的说话方式，只能靠 120 的长度上限切句，定稿会延后几秒。
- 每句独立翻译，没有上下文：代词、省略主语可能译错。
